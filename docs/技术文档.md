## 1. 项目概述

### 1.1 项目背景

CRM-OrchSell 是一个面向 B2B 实体产品销售场景的智能 Agent 系统。在传统 B2B 销售流程中，销售人员需要手动查询库存系统、价格数据库、历史成交案例，并基于这些信息撰写销售方案。该过程耗时长、数据分散、且容易因人为疏忽导致信息不准确。

本项目通过构建智能 Agent，实现"任务拆解 -> 多工具调度 -> 反思验真 -> 方案生成"的全流程自动化，将销售方案生成时间从小时级压缩到秒级，同时通过反思验真引擎保证输出数据的准确性。

### 1.2 核心能力

| 能力维度 | 描述 |
|----------|------|
| 任务拆解 | LLM 驱动，将客户咨询文本自主拆分为标准化子任务队列 |
| 多工具调度 | 按优先级分组、依赖检查、同优先级并行执行 |
| 反思验真 | 三层校验机制（边界+业务规则+数据源比对），量化幻觉风险 |
| 方案生成 | 基于真实数据生成标准化 JSON 格式销售方案 |
| 多模型兼容 | OpenAI/智谱云端 与 Qwen 本地模型一键切换 |
| RAG 检索 | LlamaIndex + Chroma 向量检索相似成交案例 |
| NL2SQL | 自然语言转 SQL 安全查询 |
| 全链路监控 | Prometheus 指标收集 + LangFuse LLM 追踪 |

## 3. 技术选型与对比

### 3.1 Web 框架：FastAPI vs Flask vs Django

| 对比维度 | FastAPI | Flask | Django |
|----------|---------|-------|--------|
| 异步支持 | 原生 async/await，ASGI 原生 | 需 async 扩展，WSGI 为主 | 部分支持，ORM 异步不完善 |
| 自动文档 | 内置 Swagger/OpenAPI | 需 flask-restx 等插件 | 需 drf-yasg 等插件 |
| 性能 | 高性能，基于 Starlette | 中等 | 较重，启动慢 |
| 类型安全 | Pydantic 原生集成 | 无 | Django ORM 有类型 |
| 学习成本 | 低，FastAPI 文档优秀 | 低 | 中，全栈框架 |
| 生态成熟度 | 成长中，生态活跃 | 成熟 | 非常成熟 |
| 适合场景 | API 服务、微服务 | 中小 Web 应用 | 全栈 Web 应用 |

**选择原因：本项目核心是提供 REST API 对接企业 CRM 系统，FastAPI 的原生异步支持完美契合 Agent 系统中大量 LLM 调用和工具并行的异步场景；内置自动文档生成降低对接成本；Pydantic 原生集成实现请求/响应强类型校验；高性能特性保障高并发场景下的响应速度。FastAPI 版本锁定 ==0.109.0 以保证 API 稳定性。**

### 3.2 Agent 框架：LlamaIndex vs LangChain vs 自研

| 对比维度 | LlamaIndex | LangChain | 自研 |
|----------|------------|-----------|------|
| RAG 原生支持 | 原生设计，VectorStoreIndex 一站式 | 需组合 Retriever + Chain | 需从零实现 |
| 工具抽象 | FunctionTool/ToolSpec 抽象 | Tool/Agent 抽象丰富 | 完全自定义 |
| 轻量程度 | 轻量，核心包聚焦 | 较重，生态庞大但臃肿 | 取决于实现 |
| 学习曲线 | 平缓，文档清晰 | 陡峭，概念繁多 | 无学习成本 |
| 向量库集成 | Chroma/Milvus/Pinecone 等即插即用 | 同样支持 | 需手动对接 |
| 社区活跃度 | 活跃，迭代快 | 非常活跃 | 无社区 |
| 定制灵活性 | 中高，可扩展 BaseTool | 高，但复杂 | 最高 |
| 生产稳定性 | 稳定，API 变动有版本管理 | 破坏性更新较多 | 取决于团队 |

**选择原因：LlamaIndex 以 RAG 为核心设计理念，与本项目"反思验真"的 RAG 策略高度契合；VectorStoreIndex + ChromaVectorStore 组合实现极简的向量检索；工具抽象层（BaseTool）与项目工具调度器无缝集成；相比 LangChain 更轻量，避免引入不必要的依赖链；相比自研，显著降低开发成本同时保证可维护性。**

### 3.3 LLM 后端：OpenAI/智谱 vs Qwen 本地 vs 其他

| 对比维度 | OpenAI/智谱(云端) | Qwen 本地(Ollama) | Claude/其他 |
|----------|-------------------|-------------------|-------------|
| 调用方式 | HTTPS API，需网络 | 本地 HTTP，低延迟 | HTTPS API |
| 数据隐私 | 数据出境风险 | 完全本地，数据不出域 | 数据出境风险 |
| 部署成本 | 按量付费，API 调用成本 | 需 GPU 服务器，固定成本 | 按量付费 |
| 模型质量 | 高，GLM-5.1/GPT 系列强 | 中高，Qwen-7B/14B 中文优秀 | 高 |
| 中文能力 | 优秀(智谱) | 优秀(阿里出品) | 良好 |
| 离线可用 | 不可用 | 完全离线可用 | 不可用 |
| 工具调用 | 原生 function calling | 支持 tool calling | 原生支持 |

**选择原因：采用双模型策略，兼顾云端和本地场景。OpenAIAdapter 兼容 OpenAI API 和智谱 AI(bigmodel.cn)，默认模型 glm-5.1，适合对模型质量要求高的生产环境且可接受 API 成本；QwenAdapter 通过 Ollama 本地部署 Qwen-7B/14B，适合数据隐私要求高或需要离线运行的场景。通过适配器模式+策略模式统一接口，运行时通过 LLM_MODE 环境变量动态切换，BaseLLMAdapter 抽象基类定义 chat()/chat_with_tools() 统一接口，实现零代码切换。**

### 3.4 向量数据库：Chroma vs Milvus vs Pinecone vs Weaviate

| 对比维度 | Chroma | Milvus | Pinecone | Weaviate |
|----------|--------|--------|----------|----------|
| 部署方式 | 嵌入式/Server | 独立集群 | 云服务 SaaS | 独立服务 |
| Python 原生 | 完全 Python 原生 | Python SDK | Python SDK | Python SDK |
| 资源占用 | 极低，单机可用 | 高，需集群资源 | 零运维(云) | 中等 |
| 持久化 | 本地文件持久化 | 分布式存储 | 云端托管 | 本地/云 |
| 适合规模 | 中小型(万级文档) | 大规模(亿级) | 任意规模 | 中大型 |
| 运维成本 | 零运维 | 高，需专业运维 | 零运维(付费) | 中等 |
| 离线支持 | 完全离线 | 可离线 | 不可离线 | 可离线 |
| 与 LlamaIndex 集成 | 官方原生集成 | 官方集成 | 官方集成 | 官方集成 |

**选择原因：Chroma 是 Python 原生的嵌入式向量数据库，零运维成本，本地文件持久化，与 LlamaIndex 官方原生集成（llama-index-vector-stores-chroma）。本项目的成交案例数据规模在万级以内，Chroma 的性能完全满足需求；嵌入式部署模式无需额外服务进程，降低系统复杂度；完全离线可用，符合数据隐私需求。相比 Milvus 的集群运维成本和 Pinecone 的云服务依赖，Chroma 是性价比最优选择。**

### 3.5 Embedding 模型：BGE-small-zh vs text-embedding-ada-002 vs M3E

| 对比维度 | BGE-small-zh-v1.5 | text-embedding-ada-002 | M3E |
|----------|-------------------|----------------------|-----|
| 语言优化 | 中文专项优化 | 多语言通用 | 中英文 |
| 部署方式 | 本地部署，FlagEmbedding | OpenAI API 云端 | 本地部署 |
| 调用成本 | 零成本 | 按量付费 | 零成本 |
| 维度 | 512维 | 1536维 | 768维 |
| 模型大小 | 约 100MB | 云端(不占用本地) | 约 400MB |
| 中文效果 | 优秀(MTEB 中文榜首) | 良好 | 优秀 |
| 离线可用 | 完全离线 | 不可离线 | 完全离线 |
| 延迟 | 本地推理，低延迟 | 网络延迟 | 本地推理 |

**选择原因：BGE-small-zh-v1.5 是智源研究院发布的中文优化 Embedding 模型，在 MTEB 中文榜单表现优秀。本地部署通过 FlagEmbedding + HuggingFaceEmbedding 加载，零 API 调用成本，完全离线可用，适合本项目 B2B 中文销售场景。512 维向量在保证检索质量的同时降低存储和计算开销。相比 ada-002 的云端依赖和按量付费，BGE 在成本和数据隐私上优势明显。**

### 3.6 数据库：SQLite vs MySQL vs PostgreSQL

| 对比维度 | SQLite | MySQL | PostgreSQL |
|----------|--------|-------|------------|
| 部署方式 | 文件嵌入，零配置 | 独立服务 | 独立服务 |
| 并发能力 | 单写入，读并发好 | 高并发 | 高并发 |
| 数据规模 | 适合中小型(GB级) | 大型(TB级) | 大型(TB级) |
| 运维成本 | 零运维 | 中等 | 中等 |
| 事务支持 | ACID(单库) | ACID | ACID+高级特性 |
| 扩展性 | 差 | 好 | 优秀 |
| 适合场景 | 开发/中小型应用 | 企业生产 | 企业生产/复杂查询 |

**选择原因：采用多数据库支持策略，DatabaseConnector 统一接口。SQLite 作为默认开发环境数据库，零配置、零运维、文件级持久化，适合开发调试和中小规模部署；MySQL 和 PostgreSQL 通过配置切换，满足企业生产环境的高并发、大数据量需求。通过 DB_TYPE 环境变量动态选择数据库类型，DatabaseConnector 单例模式管理连接，业务代码无需感知底层数据库差异。这种设计兼顾了开发便利性和生产可扩展性。**

### 3.7 缓存：Redis vs Memcached vs 内存缓存

| 对比维度 | Redis | Memcached | 内存缓存 |
|----------|-------|-----------|----------|
| 数据结构 | 丰富(String/List/Hash等) | 仅 KV | 字典 |
| 持久化 | RDB/AOF 持久化 | 无 | 无 |
| 分布式 | 原生支持集群 | 支持 | 不支持 |
| 过期策略 | TTL 精确过期 | TTL | 手动管理 |
| 适用场景 | 通用缓存/消息队列 | 纯 KV 缓存 | 单进程临时缓存 |
| 可靠性 | 高 | 中 | 低(进程重启丢失) |
| Python 集成 | redis-py 成熟 | pymemcache | 内置 dict |

**选择原因：选择 Redis 作为主缓存方案，同时内置内存缓存作为降级方案。CacheManager 在初始化时检测 REDIS_ENABLED 开关，启用则连接 Redis，连接失败或未启用时自动降级为内存字典缓存。分类 TTL 策略（库存 3600s/价格 7200s/案例 86400s）根据数据更新频率差异化设置过期时间。这种 Redis+降级设计保证了缓存服务的高可用性，即使 Redis 不可用系统仍能正常运行。**

### 3.8 监控：Prometheus+LangFuse vs ELK vs Datadog

| 对比维度 | Prometheus+LangFuse | ELK Stack | Datadog |
|----------|---------------------|-----------|---------|
| 监控维度 | 系统指标+LLM 专项 | 日志为主 | 全栈监控 |
| LLM 追踪 | LangFuse 原生 LLM 链路 | 需自行解析日志 | 有限支持 |
| 部署成本 | 开源自部署(免费) | 开源自部署(资源消耗大) | SaaS 付费 |
| 指标收集 | Pull 模式，时序数据库 | Push 日志聚合 | Agent 采集 |
| 告警能力 | AlertManager | Kibana 告警 | 内置告警 |
| Token 统计 | LangFuse 原生 Token 追踪 | 需自行解析 | 有限 |
| 可视化 | Grafana + LangFuse UI | Kibana | Datadog UI |

**选择原因：Prometheus 负责系统级指标监控（请求量、工具调用、延迟等），代码内置 prometheus_client 无需额外部署；LangFuse 专注 LLM 调用链路追踪，提供 Token 用量统计、成本分析、质量评分等 LLM 专项能力，这是 ELK 和 Datadog 不具备的。两者互补：Prometheus 保障系统健康度监控，LangFuse 保障 LLM 调用质量与成本可控。均为开源自部署方案，零许可成本。LangFuse 可通过 LANGFUSE_ENABLED 开关按需启用。**

### 3.9 数据验证：Pydantic v2 vs Marshmallow vs 手动验证

| 对比维度 | Pydantic v2 | Marshmallow | 手动验证 |
|----------|------------|-------------|----------|
| 性能 | Rust 核心，极速 | 纯 Python，较慢 | 取决于实现 |
| 类型注解 | 原生 Python type hints | 需单独定义 Schema | 无 |
| FastAPI 集成 | 原生深度集成 | 需适配 | 需适配 |
| 嵌套模型 | 优秀支持 | 支持 | 需手动实现 |
| 序列化 | 原生 JSON 序列化 | 需额外处理 | 需手动实现 |
| 校验规则 | Field 约束+validator | validate 参数 | if/else |
| 配置管理 | pydantic-settings 环境变量 | 不支持 | 需手动实现 |

**选择原因：Pydantic v2 基于 Rust 核心重写，性能远超 v1 和 Marshmallow；与 FastAPI 原生深度集成，请求/响应自动校验和文档生成；Field 约束和 validator 装饰器实现复杂业务校验规则；pydantic-settings 模块统一管理环境变量配置，BaseSettings 类自动从 .env 读取配置。项目所有数据模型（InventoryInfo、PricingInfo、SalesResponse 等）均基于 Pydantic BaseModel 定义，实现端到端类型安全。**

### 3.10 日志：Loguru vs logging vs structlog

| 对比维度 | Loguru | logging(标准库) | structlog |
|----------|--------|-----------------|-----------|
| 易用性 | 极简 API，零配置 | 需配置 Handler/Formatter | 需配置 Processor |

| 结构化日志 | 支持绑定 extra | 支持 extra | 原生结构化 |

**选择原因：Loguru 提供极简的 API（logger.info/logger.error），零配置即可使用；内置文件轮转和保留策略，自动管理日志文件大小和历史保留；自动捕获异常堆栈信息，调试友好；彩色终端输出提升开发体验。项目全局使用 loguru 记录任务拆解、工具调用、反思校验等全链路日志，日志文件按 LOG_FILE 和 LOG_LEVEL 配置输出。相比标准库 logging 的繁琐配置和 structlog 的结构化学习成本，Loguru 在易用性和功能间取得最佳平衡。**

## 4. 核心难点与解决方案

### 4.1 难点一：LLM 幻觉控制

**问题描述：**
LLM 在生成销售方案时，可能编造不存在的库存数据、价格信息或成交案例。在 B2B 销售场景中，错误的库存承诺或价格报价会导致严重的商业纠纷和信任损失。LLM 幻觉是 Agent 系统落地生产的最大障碍之一。

**影响分析：**
- 库存幻觉：承诺客户有货但实际无货，导致违约风险
- 价格幻觉：报价低于成本价或高于市场价，造成经济损失
- 案例幻觉：引用不存在的成交案例，损害企业信誉
- 信任损失：客户发现数据错误后，永久性信任丧失

**解决方案：三层反思验真引擎**

构建"BoundaryValidator + BusinessRuleValidator + 数据源比对"三层校验机制，对 Agent 输出的每一个数据字段进行事实验真，并输出 ReflectionReport 量化幻觉风险。

**技术实现：**

1. **第一层 - BoundaryValidator（数值边界校验）**
   - 库存数量：>= 0 且 <= 1,000,000
   - 价格：> 0 且 <= 10,000,000
   - 折扣率：0 ~ 1 之间
   - 采购数量：0 ~ 100,000
   - 相似度：0 ~ 1 之间

2. **第二层 - BusinessRuleValidator（业务规则校验）**
   - 可用库存 <= 总库存（不能超卖）
   - 总价 = 单价 x 数量 x 折扣率（金额一致性）
   - 折扣率在合理区间（防止异常折扣）

3. **第三层 - 数据源比对**
   - Agent 输出的库存数据与 API 查询结果比对
   - Agent 输出的价格数据与 SQL 查询结果比对
   - Agent 输出的案例数据与向量检索结果比对

4. **ReflectionReport 输出**
   - 置信度阈值：0.8
   - 置信度 >= 0.8：标记为 verified（已验真）
   - 置信度 < 0.8：标记为 partial（部分可信，需人工复核）

**效果评估：**
- 幻觉检出率：通过三层校验，可检出 90%+ 的数值类幻觉
- 误报率：边界校验基于业务规则，误报率低于 5%
- 性能开销：反思验真增加约 200-500ms 延迟，可接受
- 置信度量化：为下游系统提供可信度判断依据，支持自动/人工分流

---

### 4.2 难点二：任务依赖编排

**问题描述：**
销售 Agent 需要执行多个子任务（库存查询、价格查询、案例检索、价格计算），这些任务之间存在复杂的依赖关系。例如，价格计算依赖库存查询和价格查询的结果。如何在保证执行效率的前提下，正确编排任务依赖关系，是 Agent 系统的核心挑战。

**影响分析：**
- 依赖缺失：价格计算在价格查询未完成时执行，导致计算错误
- 并行冲突：无依赖任务串行执行，增加用户等待时间
- 超时阻塞：单个工具卡死导致整个任务链阻塞
- 结果传递：前序任务结果无法正确传递给后续任务

**解决方案：优先级分组 + 依赖检查 + 并行调度**

**技术实现：**

1. **TaskPlanner 任务拆解**
   - LLM 驱动，根据客户咨询文本拆分标准化子任务
   - 每个任务携带 priority（优先级）和 dependencies（依赖列表）
   - 任务类型：inventory_query(1) / price_query(2) / case_retrieval(2) / price_calculation(3)

2. **ToolDispatcher 优先级分组**
   ```
   priority=1: [inventory_query]          ← 第一批执行
   priority=2: [price_query, case_retrieval]  ← 第二批并行执行
   priority=3: [price_calculation]        ← 第三批执行（依赖前两批）
   ```

3. **并行执行**
   - 同优先级任务使用 asyncio.gather 并行执行
   - 不同优先级任务按顺序串行执行
   - asyncio.wait_for 设置 30s 超时保护

4. **context 依赖传递**
   - 前序任务结果通过 context[task_type] 注入后续任务参数
   - price_calculation 任务从 context["inventory_query"] 和 context["price_query"] 获取数据
   - 依赖检查：执行任务前验证所有 dependencies 是否已完成

**效果评估：**
- 执行效率：同优先级并行执行，总耗时降低 30-40%
- 依赖正确性：100% 保证依赖任务先于被依赖任务执行
- 超时容错：30s 超时保护，避免单工具卡死阻塞全链路
- 结果传递：context 字典机制实现任务间数据零损耗传递

---

### 4.3 难点三：多模型无缝切换

**问题描述：**
不同部署环境对 LLM 有不同需求：生产环境可能使用云端 API（OpenAI/智谱）追求模型质量，私有化部署可能使用本地模型（Qwen）保障数据隐私。如何让业务代码无感知地在不同 LLM 后端间切换，是系统可维护性的关键。

**影响分析：**
- 切换成本：硬编码 LLM 调用导致切换需修改大量代码
- 接口不一致：不同 LLM 的 API 参数和返回格式差异
- 测试困难：切换模型后需要全量回归测试
- 功能差异：不同模型对 function calling 的支持程度不同

**解决方案：适配器模式 + 策略模式**

**技术实现：**

1. **BaseLLMAdapter 抽象基类**
   - 定义统一接口：chat() 和 chat_with_tools()
   - 抽象方法强制子类实现，保证接口一致性
   - 所有业务代码依赖 BaseLLMAdapter，不依赖具体实现

2. **OpenAIAdapter 实现**
   - 兼容 OpenAI API 和智谱 AI(bigmodel.cn)
   - 默认模型：glm-5.1
   - 支持 function calling 工具调用

3. **QwenAdapter 实现**
   - 通过 Ollama 部署 Qwen-7B/14B
   - 本地 HTTP 调用，低延迟
   - 支持 tool calling

4. **get_llm() 工厂函数**
   - 读取 settings.LLM_MODE 环境变量
   - 运行时动态返回对应适配器实例
   - 切换模型只需修改 .env 配置，无需改代码

**效果评估：**
- 切换成本：从 OpenAI 切换到 Qwen 仅需修改 LLM_MODE=qwen，零代码改动
- 接口一致性：BaseLLMAdapter 强制统一接口，业务代码无感知
- 测试隔离：可 mock BaseLLMAdapter 进行单元测试，不依赖真实 LLM
- 扩展性：新增 LLM 后端只需继承 BaseLLMAdapter，符合开闭原则

### 4.4 难点四：NL2SQL 安全防护

**问题描述：**
NL2SQL 允许用户通过自然语言查询数据库，但 LLM 生成的 SQL 语句可能包含危险操作（DROP/DELETE/UPDATE），或查询非授权表的数据，导致数据泄露或破坏。这是 NL2SQL 系统的核心安全风险。

**影响分析：**
- 数据破坏：DROP/DELETE 等操作可能删除生产数据
- 数据泄露：查询非授权表可能暴露敏感信息
- SQL 注入：LLM 生成恶意 SQL 绕过应用层校验
- 权限滥用：用户通过 NL2SQL 执行越权操作

**解决方案：白名单 + 关键词过滤 + 只读模式**

**技术实现：**

1. **表名白名单**
   - 允许查询表：products / customers / deal_records
   - 其他表（如 users / config / system）一律拒绝
   - 在 SQL 执行前校验 FROM/JOIN 子句中的表名

2. **危险关键词过滤**
   - 禁止关键词：DROP / DELETE / UPDATE / INSERT / TRUNCATE / ALTER / CREATE
   - 禁止关键词：EXEC / EXECUTE / SP_ / XP_（防止存储过程调用）
   - 大小写不敏感匹配，防止绕过

3. **SELECT 限制**
   - 仅允许 SELECT 语句
   - 通过正则校验 SQL 语句以 SELECT 开头
   - 拒绝所有 DML/DDL 操作

4. **只读模式**
   - 连接 SQLite 时执行 PRAGMA query_only = ON
   - 数据库层面禁止任何写操作，作为最后一道防线
   - 即使前述校验被绕过，数据库层也会拒绝写操作

5. **Schema 缓存**
   - 数据库表结构信息缓存到 _schema_cache
   - 避免每次 NL2SQL 都查询 schema，提升性能

**效果评估：**
- 安全性：四层防护（白名单+关键词+SELECT限制+只读模式），纵深防御
- 性能：Schema 缓存避免重复查询，SQL 执行延迟 < 100ms
- 可维护性：白名单和关键词列表集中管理，易于更新
- 审计：所有 NL2SQL 查询记录日志，支持事后追溯

### 4.5 难点五：输出格式强约束

**问题描述：**
LLM 生成的销售方案需要对接企业 CRM 系统，要求 100% 固定的 JSON 格式。但 LLM 输出存在格式不稳定问题：可能输出 Markdown 包裹的 JSON、多余说明文字、字段缺失、类型错误等，导致下游系统解析失败。

**影响分析：**
- 解析失败：JSON 格式错误导致 CRM 系统无法解析
- 字段缺失：关键字段缺失导致方案不完整
- 类型错误：字符串数字导致下游类型校验失败
- 对接成本：格式不稳定增加人工校验成本

**解决方案：Pydantic v2 Schema + Prompt 工程**

**技术实现：**

1. **Pydantic 输出 Schema 定义**
   - SalesResponse：顶层响应模型，包含所有字段
   - InventoryInfo：库存信息子模型（product_name/stock_quantity/available_quantity/lead_time 等）
   - PricingInfo：价格信息子模型（unit_price/total_price/discount_rate/payment_terms 等）
   - CaseInfo：案例信息子模型（case_id/deal_price/similarity_score 等）
   - ProposalInfo：方案信息子模型（summary/pricing_strategy/next_steps/risk_warnings 等）
   - 所有字段使用 Field(..., description=) 强制约束和文档化

2. **Prompt 工程**
   - 系统提示词明确约束输出 JSON 格式
   - 提供 JSON 模板示例，指导 LLM 输出格式
   - 强调"数据缺失"时标注，而非编造填充

3. **输出校验与解析**
   - LLM 输出后通过 Pydantic 模型校验
   - 校验失败时记录错误日志并返回标准化错误响应
   - 反思验真引擎对输出数据做事实验真

4. **TaskLog 任务日志**
   - 每个任务执行结果封装为 TaskLog 模型
   - 包含 task_id/task_type/status/result/error 等字段
   - 标准化日志格式，便于全链路追踪

**效果评估：**
- 格式稳定性：Pydantic 强校验保证 100% 合规 JSON 输出
- 字段完整性：Field(...) 必填约束防止关键字段缺失
- 类型安全：自动类型转换和校验，避免类型错误
- 对接效率：标准化 JSON 格式，CRM 系统零适配成本

### 4.6 难点六：向量检索质量

**问题描述：**
RAG 检索的成交案例质量直接影响方案生成的准确性。中文销售场景下的语义检索面临：分词不准确、行业术语匹配失败、相似度阈值设置不当导致召回噪声或漏召回等问题。

**影响分析：**
- 召回噪声：相似度低的案例被召回，干扰方案生成
- 漏召回：相似案例未被检索到，方案缺乏参考
- 语义偏差：字面相似但语义不同的案例被误召回
- 性能问题：全量检索导致延迟过高

**解决方案：BGE 中文优化 + 相似度阈值**

**技术实现：**

1. **BGE-small-zh-v1.5 中文 Embedding**
   - FlagEmbedding 加载本地 BGE 模型
   - HuggingFaceEmbedding 与 LlamaIndex 集成
   - 中文专项优化，MTEB 中文榜单表现优秀
   - 512 维向量，平衡精度和性能

2. **LlamaIndex VectorStoreIndex**
   - VectorStoreIndex + ChromaVectorStore 组合
   - 向量索引自动管理，支持增量更新
   - similarity_top_k 参数控制召回数量（默认 3）

3. **相似度阈值过滤**
   - 相似度边界：0.0 ~ 1.0（BoundaryValidator 校验）
   - 低于阈值的案例在反思验真阶段被过滤
   - ReflectionReport 记录每个案例的 similarity_score

4. **DocRetrieveTool 检索工具**
   - 支持产品名称、数量区间、付款条件等多维查询
   - 构建查询文本时融合多个业务字段
   - 检索结果通过 CaseInfo 模型结构化

5. **缓存优化**
   - 案例检索结果缓存到 Redis（TTL 86400s）
   - 相同查询直接返回缓存，避免重复向量检索
   - 缓存降级为内存缓存，保证可用性

**效果评估：**
- 检索准确率：BGE 中文优化提升中文语义匹配度 20%+
- 召回质量：相似度阈值过滤噪声案例，Top-3 召回有效案例率 85%+
- 响应延迟：向量检索+缓存命中，平均延迟 < 500ms
- 可扩展性：支持多维查询条件，适应不同业务场景

### 4.7 难点七：工具超时容错

**问题描述：**
Agent 调度的多个工具（库存 API、价格 SQL、文档检索等）可能因网络抖动、数据库慢查询、向量检索耗时等原因卡死。单个工具超时会阻塞整个任务链，导致用户长时间等待甚至请求超时。

**影响分析：**
- 用户体验：工具卡死导致用户等待时间不可控
- 链路阻塞：串行任务中前序工具超时阻塞后续任务
- 资源浪费：超时工具持续占用连接资源
- 系统可用性：大面积工具超时可能导致服务不可用

**解决方案：asyncio.wait_for + 降级策略**

**技术实现：**

1. **asyncio.wait_for 超时控制**
   - 每个工具执行包裹在 asyncio.wait_for 中
   - 超时时间通过 settings.TOOL_TIMEOUT 配置（默认 30s）
   - 超时后抛出 asyncio.TimeoutError，不阻塞后续任务

2. **优先级分组隔离**
   - 同优先级任务并行执行，一个超时不影响其他
   - 不同优先级组之间，前组超时不完全阻塞后组
   - 超时任务标记为 failed，后续任务可获取部分结果

3. **降级策略**
   - 工具超时后返回标准化错误结果（ToolResult.success=False）
   - 方案生成阶段对缺失数据标注"数据缺失"，不编造
   - 缓存降级：Redis 不可用时自动降级为内存缓存

4. **错误封装**
   - BaseTool._handle_error() 统一处理工具异常
   - 异常信息封装为 ToolResult，不直接抛出
   - 日志记录完整堆栈信息，便于排查

5. **tenacity 重试机制**
   - 可配置的重试策略（指数退避）
   - 适用于网络抖动等临时性故障
   - 最大重试次数可配置，避免无限重试

**效果评估：**
- 超时可控：所有工具执行受 30s 超时保护，最坏情况下单任务 30s 返回
- 链路不阻塞：超时任务不影响其他任务执行，并行组内隔离
- 降级可用：工具失败后系统仍可返回部分结果，而非完全失败
- 错误可追溯：完整日志记录超时工具和堆栈信息

---

### 4.8 难点八：缓存一致性

**问题描述：**
缓存库存、价格、案例数据后，如果底层数据更新但缓存未失效，会导致 Agent 基于过期数据生成方案。B2B 销售场景中，库存和价格变化频繁，缓存一致性问题直接影响方案准确性。

**影响分析：**
- 库存超卖：缓存显示有货，实际已售罄，导致超卖
- 价格错误：缓存价格过期，报价不符合最新价格政策
- 案例过时：旧案例不再有参考价值
- 信任损失：基于过期数据的方案损害客户信任

**解决方案：分类 TTL + Redis 降级**

**技术实现：**

1. **分类 TTL 策略**
   - 库存数据 TTL = 3600s（1小时）：库存变化频繁，短 TTL
   - 价格数据 TTL = 7200s（2小时）：价格变化适中，中 TTL
   - 案例数据 TTL = 86400s（24小时）：案例变化少，长 TTL
   - 根据数据更新频率差异化设置，平衡一致性和性能

2. **CacheManager 统一管理**
   - Redis 缓存为主，内存缓存为降级方案
   - _init_redis() 初始化 Redis 连接
   - 连接失败自动降级为 _memory_cache 字典
   - REDIS_ENABLED 开关控制缓存启用

3. **缓存读写策略**
   - 读缓存：先查 Redis，未命中查内存缓存，最后查数据源
   - 写缓存：同时写 Redis 和内存缓存，保证降级后数据可用
   - 内存缓存：_get_memory_cache / _set_memory_cache 管理 TTL

4. **反思验真兜底**
   - 即使缓存数据过期，反思验真引擎仍会校验数据合理性
   - BoundaryValidator 校验数值边界
   - BusinessRuleValidator 校验业务规则
   - 数据源比对作为最终一致性保障

**效果评估：**
- 一致性：分类 TTL 根据数据特性差异化过期，一致性风险可控
- 可用性：Redis 降级为内存缓存，缓存服务可用性 99.9%+
- 性能：缓存命中率提升查询性能 3-5 倍
- 兜底保障：反思验真引擎作为最后防线，即使缓存过期也能检出异常

### 4.9 难点九：LLM 调用成本控制

**问题描述：**
Agent 系统中 LLM 调用频繁（任务拆解、方案生成、NL2SQL 等），云端 API 按量计费模式下，成本可能快速累积。如何在保证方案质量的前提下，有效控制 LLM 调用成本，是系统可持续运营的关键。

**影响分析：**
- 成本不可控：每次请求多次 LLM 调用，成本线性增长
- Token 浪费：冗长 Prompt 和无关上下文浪费 Token
- 模型选择：高质量模型成本高，低成本模型质量不足
- 缺乏监控：无法追踪 Token 用量和成本分布

**解决方案：Token 监控 + 模型切换**

**技术实现：**

1. **tiktoken Token 计数**
   - 集成 tiktoken 库统计 Token 用量
   - 每次 LLM 调用记录 input_tokens 和 output_tokens
   - 按模型定价计算调用成本

2. **LangFuse 成本追踪**
   - LangfuseMonitor 追踪每次 LLM 调用的 Token 用量
   - 自动统计成本分布（按任务类型/模型/时间维度）
   - LangFuse UI 可视化成本趋势

3. **双模型策略**
   - 高质量场景（方案生成）：使用 OpenAI/智谱 GLM-5.1
   - 低质量需求场景（任务拆解）：可切换到本地 Qwen-7B
   - LLM_MODE 环境变量动态切换，按场景选择性价比最优模型

4. **Prompt 优化**
   - 系统提示词精简，去除冗余描述
   - 任务拆解输出 JSON 格式，减少 Token 浪费
   - 方案生成 Prompt 仅包含必要数据，避免无关上下文

5. **缓存复用**
   - 案例检索结果缓存（TTL 86400s），减少重复 RAG 检索
   - 相同查询的 LLM 响应可缓存（按场景配置）
   - 任务拆解结果可按相似查询缓存

6. **Prometheus 监控**
   - llm_calls_total：LLM 调用总次数（按模型/状态维度）
   - llm_call_duration：LLM 调用耗时分布
   - 结合 Token 用量分析成本效率

**效果评估：**
- 成本可见：LangFuse 追踪每次调用的 Token 和成本，成本透明
- 成本优化：双模型策略，低优先级任务使用本地模型降低 60%+ 成本
- Token 节省：Prompt 优化和缓存复用减少 20-30% Token 消耗
- 趋势分析：LangFuse UI 提供成本趋势分析，支持容量规划

### 4.10 难点十：系统可观测性

**问题描述：**
Agent 系统链路长（任务拆解 -> 工具调度 -> 反思验真 -> 方案生成），涉及多个组件和异步调用。缺乏可观测性会导致：问题难以定位、性能瓶颈难以发现、系统健康度难以评估。

**影响分析：**
- 问题定位难：异常发生时无法快速定位是哪个环节出错
- 性能盲区：不知道哪个工具/LLM 调用是性能瓶颈
- 健康度未知：无法量化系统整体健康状态
- LLM 质量不可控：无法评估 LLM 输出质量和幻觉率

**解决方案：Prometheus + LangFuse 双监控**

**技术实现：**

1. **Prometheus 系统指标监控**
   - **请求指标**：request_total（请求总数）、request_duration（请求延迟分布）、request_concurrent（并发请求数）
   - **工具指标**：tool_calls_total（工具调用次数）、tool_call_duration（工具调用延迟）
   - **LLM 指标**：llm_calls_total（LLM 调用次数）、llm_call_duration（LLM 调用延迟）
   - **反思指标**：reflection 校验次数和通过率
   - **缓存指标**：缓存命中率和失效次数
   - **客户指标**：客户查询次数和分布
   - **健康指标**：系统健康检查端点

2. **LangFuse LLM 链路追踪**
   - 每次 LLM 调用创建 trace（追踪链路）
   - 记录 input/output/latency/cost 等维度
   - Token 用量统计（input_tokens/output_tokens）
   - 成本分析和质量评分
   - LangFuse SDK v2 API，单例模式管理
   - LANGFUSE_ENABLED 开关按需启用
   - 采样率配置控制追踪粒度

3. **Loguru 全链路日志**
   - 任务拆解日志：记录 LLM 拆解的任务列表
   - 工具调度日志：记录每个工具的执行参数和结果
   - 反思校验日志：记录校验过程和结果
   - 方案生成日志：记录最终方案输出
   - 日志文件轮转和保留策略

4. **监控指标集成**
   - MonitoringService 单例管理所有 Prometheus 指标
   - /metrics 端点暴露 Prometheus 指标供抓取
   - Grafana 可视化仪表盘（通过 Prometheus 数据源）
   - LangFuse UI 可视化 LLM 调用链路

**效果评估：**
- 全链路可观测：从请求到响应的完整链路追踪
- 问题定位：日志+指标+追踪三维度定位，平均定位时间 < 5 分钟
- 性能分析：Histogram 指标分析各环节延迟分布，识别瓶颈
- LLM 质量监控：LangFuse 追踪 LLM 调用质量和成本
- 系统健康：Prometheus + 健康检查端点实时评估系统状态

## 5. LLM 适配层

### 5.1 架构设计

LLM 适配层采用"适配器模式 + 策略模式"设计，通过抽象基类统一接口，具体实现类封装不同 LLM 后端的调用逻辑。

```
BaseLLMAdapter (抽象基类)
├── chat()              ← 统一聊天接口
├── chat_with_tools()   ← 统一带工具调用接口
│
├── OpenAIAdapter       ← OpenAI/智谱适配器
│   ├── 模型: glm-5.1 (默认)
│   ├── API: bigmodel.cn / openai.com
│   └── 特性: function calling 原生支持
│
└── QwenAdapter         ← Qwen 本地适配器
    ├── 模型: qwen:7b / qwen:14b
    ├── API: ollama localhost:11434
    └── 特性: 本地部署，离线可用
```

### 5.2 关键接口

| 接口 | 参数 | 返回 | 说明 |
|------|------|------|------|
| chat() | messages, temperature, max_tokens | str | 普通聊天补全 |
| chat_with_tools() | messages, tools, temperature | Dict | 带工具调用的聊天补全 |

### 5.3 切换机制

- `get_llm()` 工厂函数读取 `settings.LLM_MODE` 环境变量
- `LLM_MODE=openai`：返回 OpenAIAdapter 实例
- `LLM_MODE=qwen`：返回 QwenAdapter 实例
- 业务代码通过 `get_llm()` 获取适配器，不直接实例化具体类
- LangfuseMonitor 延迟导入，避免启动时依赖问题

## 6. RAG 实现细节

### 6.1 技术架构

```
用户查询 → BGE-small-zh-v1.5 Embedding → Chroma 向量检索 → Top-K 相似案例 → 反思验真过滤
```

### 6.2 核心组件

| 组件 | 技术 | 说明 |
|------|------|------|
| Embedding 模型 | BGE-small-zh-v1.5 | 中文优化，512 维，本地部署 |
| Embedding 加载 | FlagEmbedding + HuggingFaceEmbedding | 双库加载，兼容 LlamaIndex |
| 向量存储 | ChromaVectorStore | LlamaIndex 原生集成 |
| 索引管理 | VectorStoreIndex | 自动管理向量索引 |
| 检索工具 | DocRetrieveTool | 从 Chroma 检索相似成交案例 |

### 6.3 双模式支持

- **在线模式**：通过 LlamaIndex VectorStoreIndex 在线检索
- **本地模式**：Chroma 本地文件持久化，离线可用
- 两种模式通过配置切换，业务代码无感知

### 6.4 检索流程

1. DocRetrieveTool 接收查询参数（product_name/quantity_range/payment_terms）
2. 构建查询文本，融合多个业务字段
3. 尝试从缓存获取（Redis TTL 86400s）
4. 缓存未命中：调用 VectorStoreIndex.retrieve() 向量检索
5. 返回 Top-K（默认 3）相似案例，结构化为 CaseInfo 模型
6. 每个案例附带 similarity_score（相似度得分）

## 7. 反思验真引擎

### 7.1 三层校验架构

```
Agent 输出
    │
    ▼
┌────────────────────────────────┐
│ 第一层：BoundaryValidator      │ ← 数值边界校验
│ - 库存: 0 ~ 1,000,000          │
│ - 价格: 0 ~ 10,000,000         │
│ - 折扣: 0 ~ 1                  │
│ - 相似度: 0 ~ 1                │
└────────────┬───────────────────┘
             │ 通过
             ▼
┌────────────────────────────────┐
│ 第二层：BusinessRuleValidator  │ ← 业务规则校验
│ - 可用库存 <= 总库存            │
│ - 总价 = 单价 × 数量 × 折扣     │
│ - 折扣在合理区间                │
└────────────┬───────────────────┘
             │ 通过
             ▼
┌────────────────────────────────┐
│ 第三层：数据源比对              │ ← 事实验真
│ - 库存数据 vs API 查询结果      │
│ - 价格数据 vs SQL 查询结果      │
│ - 案例数据 vs 向量检索结果      │
└────────────┬───────────────────┘
             │
             ▼
    ReflectionReport
    - 置信度 (0.0 ~ 1.0)
    - 状态: verified / partial
    - 阈值: 0.8
```

### 7.2 ReflectionReport 输出

| 字段 | 类型 | 说明 |
|------|------|------|
| confidence | float | 综合置信度（0.0 ~ 1.0） |
| status | str | 验真状态：verified(>=0.8) / partial(<0.8) |
| field_reports | List[ReflectionField] | 各字段校验明细 |
| errors | List[str] | 校验错误列表 |

### 7.3 置信度阈值策略

- **置信度 >= 0.8**：标记为 `verified`，数据可信，可自动采纳
- **置信度 < 0.8**：标记为 `partial`，数据部分可信，需人工复核
- 阈值通过 `Constants` 配置，可按业务需求调整

## 9. 工具调度机制

### 9.1 调度流程

```
TaskPlanner 拆解任务
    │
    ▼
TaskPlan 列表 (含 priority + dependencies)
    │
    ▼
ToolDispatcher.dispatch()
    │
    ├── 按优先级分组 (_group_by_priority)
    │
    ├── priority=1: [inventory_query]
    │   └── asyncio.wait_for(execute, 30s) → context["inventory_query"]
    │
    ├── priority=2: [price_query, case_retrieval]
    │   └── asyncio.gather(并行执行) → context["price_query"], context["case_retrieval"]
    │
    └── priority=3: [price_calculation]
        └── 从 context 获取依赖数据 → 执行计算
```

### 9.2 关键机制

| 机制 | 实现 | 说明 |
|------|------|------|
| 优先级分组 | _group_by_priority() | 按 priority 字段分组 |
| 依赖检查 | dependencies 字段 | 执行前校验依赖任务已完成 |
| 并行执行 | asyncio.gather() | 同优先级任务并行 |
| 超时保护 | asyncio.wait_for() | 默认 30s 超时 |
| 结果传递 | context[task_type] | 前序结果注入后续任务参数 |
| 工具注册 | register_tool() | 动态注册工具实例 |

### 9.3 任务类型与优先级

| 任务类型 | 优先级 | 执行工具 | 依赖 |
|----------|--------|----------|------|
| inventory_query | 1 | api_inventory | 无 |
| price_query | 2 | sql_price | 无 |
| case_retrieval | 2 | doc_retrieve | 无 |
| price_calculation | 3 | calculator | inventory_query, price_query |

## 11. 缓存策略

### 11.1 CacheManager 架构

```
CacheManager
├── Redis 缓存 (主)
│   ├── _init_redis() → redis.Redis 客户端
│   ├── socket_timeout: 5s
│   └── decode_responses: True
│
└── 内存缓存 (降级)
    ├── _memory_cache: Dict[str, Any]
    ├── _get_memory_cache(key) → 检查 TTL 过期
    └── _set_memory_cache(key, value, ttl)
```

### 11.2 分类 TTL 策略

| 数据类型 | TTL | 配置项 | 原因 |
|----------|-----|--------|------|
| 库存数据 | 3600s (1小时) | CACHE_TTL_INVENTORY | 库存变化频繁 |
| 价格数据 | 7200s (2小时) | CACHE_TTL_PRICING | 价格变化适中 |
| 案例数据 | 86400s (24小时) | CACHE_TTL_CASES | 案例变化少 |

### 11.3 降级机制

1. `REDIS_ENABLED=False`：直接使用内存缓存
2. Redis 连接失败：自动降级为内存缓存，记录错误日志
3. 内存缓存通过 `expire_at` 时间戳管理 TTL
4. 降级后系统功能不受影响，仅缓存持久性降低

| 编号 | 问题描述 | 风险等级 | 影响范围 | 建议修复方案 |
